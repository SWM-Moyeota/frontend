### 판단 기록

- **기기 식별자는 「무작위」로 적었다.** Mixpanel Swift SDK 7.0.0 은 `useUniqueDistinctId` 를 켜지 않으면 `UUID()` 를 쓴다
  (`MixpanelInstance.defaultDeviceId`). IDFV 가 아니다. frontend-ios `PrivacyInfo.xcprivacy` 의 주석 「IDFV 기반」은 같은 날 고쳤다.
- **IP 주소가 Mixpanel 에 전달된다고 적었다.** SDK 가 `?ip=1` 로 보내고 Mixpanel 이 국가·도시를 붙인다. Mixpanel 이 IP 원문을
  얼마나 보관하는지는 실측하지 못해 적지 않았다 — 「전달된다」까지만.
- **보관 기간은 「회원 탈퇴 시까지(삭제 요청)」로 적었다.** Mixpanel 쪽 자동 삭제가 없으니 모여타가 지워야 참이 된다.
  **운영 할 일이 생긴다** — `delete_account` 이벤트가 오면 Mixpanel Users → 프로필 → Delete(또는 GDPR API). 이 절차를 지키지
  않을 거면 이 줄을 「보관 기간을 정해두지 않았습니다」로 바꿔야 한다. 자동화하면 그때 문구를 「자동으로」로 올린다.
- **플랫폼 구분 없이 「앱」으로 적었다(오너 결정, 11-05).** 처음엔 「iPhone 앱에서만」으로 썼으나 Android 가 같은 Mixpanel
  프로젝트로 곧 따라올 예정이라 한 번의 개정·공지로 끝내기로 했다. 이 항목을 쓸 때 Android 앱에는 아직 Mixpanel 코드가 없었으므로 제9조 제3항과
  개정 이력에 「Android 앱은 이 기능이 들어간 업데이트부터」라고 적어 시점을 못 박았다(11-01 의 「이 시행일 이후 배포되는 버전부터」와
  같은 방식). Android 가 실제로 붙으면 이 문서는 고칠 것이 없고, 혹시 Android 계획이 취소되면 그 문장을 지워야 한다. 안드로이드 쪽 계약 문서는 `~/Documents/notes/moyeota/2026-11-03-mixpanel-이벤트-설계와-iOS-연동-정리.md`.
- **시행일은 당일(11-05) — 오너 결정(2026-11-05).** 11-01·11-03 과 같은 선택이다. 제16조의 30일 공지를 또 지키지 못하며,
  이번에는 App Store 에 실사용자가 있다. 30일을 지키려면 시행일을 2026-12-05 로 바꾸고 App Store 제출을 그 뒤로 미루거나,
  Mixpanel 토큰을 비운 빌드를 먼저 내보내야 한다(토큰이 비면 SDK 가 꺼진다). 어느 쪽이든 결정을 여기에 적는다.
- **공지문은 `_notice-20261105-mixpanel.md`.** 보낼지와 채널은 오너가 정한다. 지금 App Store 의 1.0.1 에는 이 수집이 없으므로
  문구는 「다음 업데이트부터」다.

### 같은 날 추가 — Android 앱이 붙었다 (frontend PR #76)

Android 앱에 iOS 와 같은 계약으로 Mixpanel 이 들어갔다(`feature/mixpanel-analytics-v2`, `docs/ANALYTICS.md`, 같은 프로젝트
codingforest 4080134·같은 토큰). 「이 기능이 들어간 업데이트부터」라는 시점 문장은 그대로 참이라 두었고, 본문에서 고친 것은
**Android SDK 가 자동으로 붙이는 항목이 iOS 와 다르다**는 한 가지다.

| 자리 | 조치 | 근거 |
|---|---|---|
| privacy 제1조 표3 「앱 이용 기록」 | 「Android 앱은 기기 제조사, 통신사 이름, 블루투스가 켜져 있는지와 그 버전, NFC·전화 기능이 있는지도 함께 붙습니다」 | 아래 SDK 확인 |
| privacy 제7조 표6 Mixpanel 행 | 같은 항목을 괄호로 | |

- **Android SDK 8.12.0 이 모든 이벤트에 자동으로 붙이는 키(바이트코드 `AnalyticsMessages$Worker$AnalyticsMessageHandler.getDefaultEventProperties` 에서 확인):**
  `$app_version`·`$app_version_string`·`$app_release`·`$app_build_number`, `$os`·`$os_version`, `$manufacturer`·`$brand`·`$model`,
  `$screen_dpi`·`$screen_height`·`$screen_width`, `$wifi`, `$carrier`, `$bluetooth_enabled`·`$bluetooth_version`, `$has_nfc`·`$has_telephone`, `$lib_version`·`mp_lib`.
  iOS 목록(11-05 본문)에 없는 것은 제조사·브랜드, 통신사, 블루투스, NFC·전화 유무 — 이것만 「Android 앱은」으로 덧붙였다.
- **IP 전달은 Android 도 같다.** `MPConfig.UseIpAddressForGeolocation` 기본값 `true`(바이트코드 `iconst_1`), 앱이 끄지 않았다.
- **기기 식별자는 Android 도 무작위.** `PersistentIdentity` 가 `java.util.UUID.randomUUID()` 로 만든다. `ANDROID_ID` 를 읽는 코드 없음.
  광고 식별자(ADID)도 읽지 않는다 — 앱 `MixpanelAnalyticsReporter.kt` 가 SDK 를 아는 유일한 파일이고 거기에 없다.
- **앱이 직접 보내는 값은 iOS 와 같다.** `domain/.../analytics/Analytics.kt` 의 sealed class 가 전부이고, `AnalyticsTest`·`*AnalyticsTest`(presentation 607건)로 고정.
  People 프로필에 `gender`·`age_band`, `identify(publicId)`, 로그아웃·탈퇴 시 `reset`.
- **탈퇴 시 Mixpanel 삭제 요청은 Android 도 수동.** `delete_account` 이벤트가 열쇠인 것은 같다.
- 검증: `python3 -I _check.py .` 실패 0.

## 2026-11-01 — 채팅 신고·Crashlytics 수집 항목 추가 (프로덕션 첫 게시 전)

안 고친 것: `index.html`, `terms/index.html`, `account-deletion/index.html`, `assets/style.css`

### 왜 고쳤나

프로덕션 트랙 게시 직전이고, 그 전에 머지된 두 변경이 이 방침과 어긋났다.

| 어긋난 자리 | 무엇이 틀렸나 | 조치 |
|---|---|---|
| 제1조 표3 | **채팅 신고**가 사유 + 직접 적은 설명(최대 500자) + 대상 메시지를 서버로 보내는데 수집 항목에 0건 | 행 추가 |
| 제11조 | 「자주 가는 곳을 하나씩 삭제해 달라는 요구는 이메일로 받는다」 — 이제 앱에서 직접 지운다 | 1항(앱 기능)으로 이동. 프로필 사진 변경·지난 탑승 기록 열람도 추가 |
| **제9조** | 제목이 「광고·분석 도구를 사용하지 않습니다」이고 본문이 **Crashlytics 를 이름까지 들어 부정**한다 | 전면 개정 |

| 제1조 표3 · 제6조 표5 · 제7조 표6 | 오류 진단 수집·보관·제3자 제공이 어디에도 없음 | 각각 행 추가 |

### 판단 기록

- **보관 기간에 숫자를 적지 않았다.** Google 의 Crashlytics 보관 기간을 실측하지 못했고,
  그 값은 모여타가 정하는 것도 아니다. 「Google 정책에 따릅니다」로 적었다.
  이 저장소 규약대로 **기억으로 숫자를 박지 않는다.**
- **`setUserId` 를 쓰지 않기로 했다.** `publicId` 는 서버에서 실명·휴대폰번호로 되짚히는
  계정 식별자여서, 보내는 순간 오류 보고가 「이용자와 연결된 데이터」가 된다. 그래서 제9조에
  「계정 식별자를 보내지 않는다」를 **약속으로 적을 수 있었다** — 코드가 그렇게 돼 있다.
- **응답 본문이 새지 않도록 코드로 막았다.** kotlinx.serialization 의 파싱 실패 메시지는
  응답 본문 조각을 그대로 담는다. `CrashlyticsErrorReporter.sanitize` 가 원본 예외를 넘기지 않고
  종류와 지점만 남긴 예외를 새로 만들어 보낸다. 제9조의 그 문장은 주석이 아니라 코드가 지킨다.
- **앱 세션 정보를 함께 적었다.** `firebase-crashlytics:20.1.0` 이 `firebase-sessions:3.0.7` 을
  전이 의존으로 끌고 온다(2026-11-01 `./gradlew :app:dependencies --configuration
  releaseRuntimeClasspath` 실측). 앱 실행 사실과 시각이 Google 로 가므로 고지에 넣었다.
  행태 분석(화면·클릭)은 여전히 없다 — `firebase-analytics` 는 의존 목록에 없다.

### 시행일을 2026-11-01 로 올렸다 — 확인이 필요한 자리

10-14 때와 달리 이번에는 **날짜를 바꾸고 개정 이력에도 줄을 넣었다.** 수집 항목이 늘어나는
변경이라 교정이 아니라 개정이기 때문이다.

다만 제16조 제1항은 「수집 항목이 늘어나는 등 중요한 변경은 **시행일 30일 전부터** 공지한다」고
약속한다. 지금 이 방침에 동의한 이용자는 **비공개 테스트 참여자뿐**이고, 늘어난 수집은
**이 시행일 이후 배포되는 빌드부터** 시작된다(개정 이력 칸에 그 사실을 적었다). 그래서
기존 이용자에게 실제로 수집이 늘어나는 시점은 그들이 새 버전으로 올라간 뒤다.

**30일 공지를 생략한 셈이므로 조치가 필요했다. 오너 결정은 「직접 공지」다(2026-11-01).**

### 3-2. 채팅 메시지 삭제 — 앱에 기능이 없다 (문서 세 건이 서로 다른 말을 하고 있었다)

**`presentation` 에서 이걸 부르는 자리가 0건이다.** 채팅 화면에 길게 누르기도 없다
(`combinedClickable`·`onLongClick` 전체 0건). `ChatRoute` 의 액션은 전송·음소거·검색·방 나가기뿐이다.

### 3-3. 위치 공유 메시지 — 처리방침 안에서 자기 모순

제3조 4항은 「현재 버전에는 내 실시간 위치를 동승자에게 공유하는 기능이 없습니다」인데
제4조 4항은 「위치를 공유하는 메시지는 …「위치를 공유했습니다」가 전달됩니다」로 적혀
읽는 사람이 둘 중 무엇이 참인지 알 수 없었다.

**사실**: 서버에는 남아 있다 — `ChatLocationController`(`POST/DELETE …/location/sharing`),
`ChatNotificationListener:29` 의 `LOCATION_PREVIEW = "위치를 공유했습니다"`,
`ChatMessageType.LOCATION`. 그런데 **앱 `ChatApi` 에 위치 관련 엔드포인트가 없고**
위치 공유 UI 는 프론트 `976f965` 로 걷어냈다(「위치 공유(2건) — 기능이 삭제됐는데…」).
앱이 받아 그릴 수는 있어도(`ChatListScreen.kt:124`) **보낼 길이 없다.**

→ 제4조 4항 끝에 「**다만 현재 앱에는 위치를 공유하는 기능이 없어 이 메시지가
만들어지지 않습니다**(제3조 제4항)」를 붙여 두 조항을 묶었다.

### 3-4. 회원 탈퇴 — 문서가 이미 맞다 (고치지 않음)

서버 `UserDeletionController`(`DELETE /api/v1/users/me`, 비밀번호 본인 확인,
`ONGOING_PARTY_EXISTS` 차단)와 앱 37 화면(`mypage/AccountDeleteScreen.kt`,
`AccountDeleteRoute.kt`, `UserApi.deleteAccount`)이 모두 있다.

앱 전체가 아직 미출시라 「앱에서 탈퇴할 수 있다」는 서술은 출시와 함께 참이 된다.

## 4. 찾았지만 고치지 않은 것 (확신이 부족하거나 지금은 문제 아님)

1. **처리방침 제12조 3항** 「암호화하지 않고 저장하는 정보 … **신고 기록의 위치**」 —
   긴급 신고가 조건부가 되면서 이 목록의 마지막 항목도 조건부지만, 이 조는 *수집*이 아니라
   *저장 방식*을 말하는 자리라 문장을 건드리지 않았다. 조건부 단서는 제1조·제3조·제6조·제10조에
   이미 네 번 들어가 있다.
2. **채팅 메시지 신고(`chat_report`)** — 서버에 `POST /api/v1/chat-rooms/{id}/reports` 와
   `chat_report` 테이블(V6)이 있는데 **앱에는 이 API 가 없다.** 그래서 약관 제15조 1항의
   「메일로 알려 주세요」는 지금 참이고, 처리방침 제1조가 이 기록을 수집 항목에 넣지 않은 것도
   맞다. 앱에 신고 UI 가 붙는 순간 **처리방침 제1조·제6조에 「채팅 신고 기록」 줄을 넣어야 한다.**
3. **약관 제17조 2항** 「다른 이용자에게 보이는 정보는 **닉네임과 지금까지의 탑승 횟수뿐**」 vs
   **처리방침 제5조 1항** 「닉네임, 누적 합승 완료 횟수, **프로필 이미지**」 — 처리방침이 더 정확하다
   (프로필 사진 업로드 기능이 없어 늘 기본 이미지다. 앱에 업로드 코드 0건). 약관의 「뿐」이
   사실을 줄이는 쪽이 아니라서 모순으로 보지 않고 그대로 뒀다.
4. **「같은 방향으로 가는 사람을 모아…」** (`index.html` 히어로, 약관 제1조, 처리방침 머리말) —
   서비스의 목적 서술이고 기능 주장이 아니라서 남겼다. 기능을 설명하던
   약관 제4조 1항 1호와 처리방침 제2조 2호만 고쳤다.
5. **시행일·개정 이력** — 위 머리말에 적은 이유로 바꾸지 않았다.

## 2026-11-03 (2차) — 용어: 「합승」 → 「동승」

운영 결정으로 서비스 설명 전반에서 「합승」을 쓰지 않고 「동승」을 쓴다(「합승」은 택시발전법상 규제 용어).
네 문서(index · privacy · terms · account-deletion)의 「합승」 59곳을 기계적으로 「동승」으로 바꿨다.
버튼 이름 「합승 완료」도 「동승 완료」로 바꿨다 — **앱의 실제 버튼 이름이 바뀌었는지 확인할 것.**
조항 번호·구조·의미는 그대로다(`_check.py` 통과). 시행일·최종 수정일은 손대지 않았다 —
용어 교체만으로 개정 공지 대상이 되는지는 운영자가 판단한다.
