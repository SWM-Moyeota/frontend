# 동승 모드 / 택시 모드 — 화면 분기표

모여타 앱은 **APK 하나**로 두 서비스 모양을 낸다.

| | 동승 모드 (COMPANION) | 택시 모드 (TAXI) |
|---|---|---|
| 누가 쓰나 | **실사용자** (현재 배포 서버) | 개발·발표·평가 |
| 서버 설정 | `TAXI_ENABLED=false` → `GET /api/v1/config` `{ "taxiEnabled": false }` | `TAXI_ENABLED=true` |
| 정원이 차면 | 방이 `COMPLETED` 에 머문다. 채팅으로 만나 직접 택시를 탄다 | 서버가 즉시 기사 매칭을 시작한다 (`DISPATCHING`) |
| 끝내는 법 | 참여자가 「합승 완료」(`POST /matching/rooms/{id}/finish`) 또는 30분 방치 스윕 | 기사 운행 종료(`FINISHED`) |
| 앱이 못 받았을 때 | **이 모드가 기본값** (`AppConfig.Default`) | — |

모드 값의 흐름: 서버 → `AppConfigViewModel.serverConfig` → (디버그 강제값) → `AppConfigViewModel.config` → 화면.
코드의 모드 개념은 `presentation/core/AppMode.kt`.

## 원칙

1. **모드는 문구와 버튼을 가른다. 화면 이동은 서버 status 가 정한다.**
   동승 모드 서버는 `DISPATCHING`·`ONGOING` 을 내지 않으므로 25·26·33 에 닿을 길이 없다.
   그런데도 그 단계가 보이면 서버가 택시 모드라는 뜻이다(앱 설정이 낡음). 이때 앱은 status 를 따라
   25·26 으로 가고 설정만 다시 읽는다 — 실제로 기사가 오는 방을 21 에 가둬 두는 쪽이 더 큰 사고다.
2. **모르면 동승.** 설정 조회 실패·응답에 키 없음 → 동승 모드. 실사용자 서버가 동승 모드라 틀려도 같은 화면이다.
3. **택시 화면은 지우지 않는다.** 25·26·33 과 그 ViewModel·테스트는 그대로 develop 에 둔다.
   동승 모드에서 보이지 않을 뿐이다. 택시 작업은 계속 develop 에서, 이 분기 뒤에서 한다.
4. **새 화면·문구를 만들 때** 두 모드 중 어디서 보이는지 아래 표에 한 줄 추가한다.

## 개발할 때

- **동승 화면 확인**: 배포 서버 그대로. 설정이 동승이다.
- **21 의 택시 문구만 확인**: 35 마이페이지 → 개발자 옵션 → 「택시 강제」. 서버가 동승이라 25 로 넘어가진 않는다.
- **25·26·33 확인**: 로컬 백엔드를 `TAXI_ENABLED=true` 로 띄우고 `MOYEOTA_BASE_URL=http://10.0.2.2:8080/` 로 빌드.
  기사 앱(frontend-driver) 또는 기사측 API 호출로 배차·운행 전이를 만든다.
- 강제값은 메모리에만 있다. 앱을 완전히 종료하면 서버 값으로 돌아간다.

## 서버 모드를 바꿀 때 (운영)

`TAXI_ENABLED` 를 바꾸고 서버를 재기동하면 **앱 업데이트 없이** 모드가 바뀐다. 앱은 다음 실행 때 새 값을 받는다.
이미 떠 있는 앱은 진행 중 방의 status 가 택시 단계로 바뀌는 순간 설정을 다시 읽는다(원칙 1).
